### 3.1 功能测试专项

> 参考测试设计方向
>
> - API 语义验证：验证 HTTP 状态码（2xx, 4xx, 5xx）的使用是否符合 RESTful 规范。
> - 边界与非法输入：验证大数据量、空字段、特殊字符及非法 JSON 格式的拦截能力。
> - 业务状态机闭环：验证资源从"创建中"到"运行中"再到"已释放"的全生命周期逻辑。

**issue #100（calculator-umbrella 增加开平方运算）功能测试要点：**

- API 契约验证 - 正常输入：POST /api/sqrt 请求体 `{"value": <非负数>}` 返回 HTTP 200，响应体 `{"result": <number>}`，结果精确到6位小数
- API 契约验证 - 负数输入：POST /api/sqrt 请求体 `{"value": <负数>}` 返回 HTTP 400，响应体 `{"error": "value must be non-negative"}`
- API 契约验证 - 非 number 输入：POST /api/sqrt 请求体 `{"value": <string/null/array/object>}` 返回 HTTP 400，响应体包含统一错误格式
- API 契约验证 - 缺参：POST /api/sqrt 请求体 `{}` 或无请求体返回 HTTP 400，响应体包含统一错误格式
- 边界值测试：value=0 → result=0；value=1 → result=1；value=16 → result=4；value=2 → result≈1.414214（精确到6位小数）

### 3.2 体验测试专项

> 参考测试设计方向
>
> - 无效引导：是否有空数据界面设计，引导用户去执行操作；是否滥用用户引导；是否有不可点击的效果。
> - 页面易用性：菜单层次是否太深；网站页面是否过长，内容过多，引起浏览者视觉疲劳；一次是否载入太多的数据；交互流程分支是否太多。
> - 设计易用性：标签页是否跟内容没有从属关系，当切换标签的时候，内容跟着切换；操作应该有主次从属关系；导航是否友好，不知如何返回上一页，不知当前页面在哪个栏目下；过于复杂的验证码，不清晰的验证码。
> - 页面性能：页面加载，下载时间是否过长，是否在合理的加载范围内；页面是否有过多新窗口，大量占用计算机资源。
> - 页面信息：是否有死链接或者链接错误；是否有页面安全信息；过于复杂的验证码，不清晰的验证码。

**issue #100 体验测试要点：**

- 新增按钮易用性验证：√ 按钮位于百分比按钮旁，图标清晰可识别，点击响应及时，符合用户习惯
- 错误提示体验验证：输入负数时弹出 toast 提示，提示信息明确（"value must be non-negative"），显示框不被污染，用户能理解错误原因并修正输入
- 结果展示体验验证：开平方结果在主显示框显示，精度展示正确（后端返回原始数字，前端展示去掉末尾零）

### 3.3 集成测试专项

> 参考测试设计方向
>
> - 协议兼容性：验证不同版本的组件间（如旧版网关与新版后端）通过 gRPC/HTTP 通信的兼容性。
> - 分布式事务/最终一致性：验证跨数据库操作或跨服务调用时，在网络波动下的数据对齐情况。
> - 全链路追踪覆盖：确保 TraceID 在所有微服务节点间透传，无断链现象。

**issue #100 集成测试要点：**

- 前后端集成验证：前端点击 √ 按钮后，正确调用后端 `/api/sqrt`，请求格式 `{"value": <输入值>}`，响应正确显示在主显示框
- 错误处理集成验证：前端点击 √ 按钮输入负数时，后端返回 HTTP 400，前端弹出 toast 提示，显示框不被污染（保持原值或清空）
- OpenAPI 契约集成验证：OpenAPI schema 已更新，包含 `/api/sqrt` 端点定义，前端可基于 schema 进行接口调用

### 3.7 性能与可伸缩性专项

> 参考测试设计方向
>

- 并发性能验证：10 并发请求下，P99 延迟 < 10ms，无错误响应
